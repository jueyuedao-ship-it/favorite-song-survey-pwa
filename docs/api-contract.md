# Favorite song survey API v1

The source of JSON types is `shared/contracts.ts`. All routes below are under `/api/v1`. Success is `{data: T}`; errors are `{error:{code,message}}`. Dates are `YYYY-MM-DD` in Japan; ranges include both endpoints. Timestamps are UTC ISO strings. GET business lists use `{items,next_cursor}`; `limit` defaults to 100, maximum 200, `cursor` is the last row ID. No SQL strings are accepted.

Every business mutation requires `operation_id` (client UUID recommended, 8–128 characters). PATCH/DELETE additionally require integer `expected_revision`; DELETE has a JSON body. A successful replay with identical authenticated actor/path/body returns the original response and HTTP status. Reusing an operation ID for another payload returns 409 `IDEMPOTENCY_CONFLICT`. IDs generated by server are opaque UUIDs. Update conflicts, same-day duplicates, name duplicates, resolving into an existing participant/version/day, and exhausted invites return 409. All mutations atomically store rows, audit, replay result, and append-only feed events. Deleted rows remain tombstones in admin/export/feed.

## Authentication

All authenticated requests use `Authorization: Bearer TOKEN`. Public participant selection never grants write rights. Guest authorization derives participant from the active device's hashed capability; supplying another `participant_id` returns 403. Store the device secret with the identity in browser persistence before first submission. Keep queued creates bound to that identity and original operation ID.

For guest or invite secrets generate **32 random bytes using crypto.getRandomValues**, encode base64url without padding (43 characters). Secrets appear only in credential issuance/claim bodies and the frontend credential store, never in business objects, audit or export. The server stores SHA-256 hashes. A secret is a bearer credential and must never be derived from a name/password/date.

Admin sessions expire after 8h. Admin password verifier secret format is `pbkdf2$100000$SALT_HEX$KEY_HEX`, using PBKDF2-HMAC-SHA256 with 100,000 iterations, 16 random salt bytes, 32 derived key bytes; more iterations are rejected for Workers compatibility. Generate locally with Node crypto.randomBytes / pbkdf2Sync; never paste passwords/verifiers into chat, logs, CLI arguments, git or public code. Collector `SYNC_TOKEN_HASH` is lowercase hex SHA-256 of a separately generated high-entropy bearer token; collector uses the original token. Configure with local Cloudflare secret tooling. API keys/verifiers are omitted from every response.

List-row editing is restricted to `EditableTable`: participants, works, versions, entities, aliases, credits, tags, tag_assignments, sources. Every table's `values` is checked against its typed whitelist; unknown/protected fields are 400. Research tables, audit, device/invite credentials and usage counters cannot be edited through generic data routes. Public business table reads are admin-only, and rows never contain auth hashes. Referenced rows must exist and be active. Reassigning an unresolved record to a version reports conflicts rather than deleting/merging records. Catalog corrections through admin set `manual_lock:true` on work/version/entity/credit/tag_assignment rows. Research must retain such fields. Tag deletion removes it from current statistics but keeps historical assignments; deleting referenced participant/version/entity/work is rejected while active dependents exist.

## Collector

These routes require the dedicated sync bearer (admin/guest rejected).

| Route            | Body/query                                                                                             | Data                  |
| ---------------- | ------------------------------------------------------------------------------------------------------ | --------------------- |
| GET `/sync/feed` | `cursor` numeric default 0, `limit` default 100 max 200, `schema_version=1`, optional `high_watermark` | `SyncFeed`            |
| POST `/sync/ack` | `{collector_id,cursor,schema_version:1}`                                                               | `SyncAcknowledgement` |

First page captures high_watermark atomically with its read. Persist that watermark and pass it on every subsequent page of the run. Events always increase sequence, up to that watermark. next_cursor is the last delivered sequence (or watermark at end); has_more controls paging. Each event carries a complete sanitized business row; collector upserts by table/id, stores tombstones and applies its local transaction before advancing cursor. The 50 seeded tags also have bootstrap feed events. On schema mismatch, negative/ahead-of-server cursor, or invalid watermark return 409 and retain the local mirror/cursor; never reset/drop data automatically. New events after the captured watermark wait for the next run. Acknowledgements cannot regress and cannot exceed server watermark. The export/feed exclude operations, admin_sessions, credential hashes, login throttle records and secret payloads. JSON export reads one D1 batch snapshot.

## Error and browser behavior

400 `INVALID_INPUT`, 401 `UNAUTHORIZED`, 403 `FORBIDDEN`, 404 `NOT_FOUND`, 409 `CONFLICT`/`IDEMPOTENCY_CONFLICT`/`SCHEMA_MISMATCH`/`CURSOR_INVALID`, 429 `RATE_LIMITED`, 503 `NOT_CONFIGURED`/`DATABASE_UNAVAILABLE`. Error text is safe and never includes SQL/raw body/secret. CORS accepts only ALLOWED_ORIGINS and bearer Content-Type requests; no cookies, no wildcard credentials. OPTIONS returns 204 for allowed origins. Responses set no-store. Health config flags can drive setup notices; no fake research success when runner/API keys are absent. Future record dates are 400. Reference URLs accept public HTTPS; private literal/IPv6/local hosts are rejected. Known YouTube watch/short/embed URLs canonicalize by the 11-character recording ID; duplicate canonical recording URLs report 409; equal titles never merge.

## D1 storage and research integration

Each business table contains `id`, `data` (validated JSON matching its shared type), and an indexed generated `revision`. Separate device/invite credentials and admin_sessions are excluded from business schemas. SQL expression indexes enforce daily uniqueness and known-recording URL uniqueness. Business-table insert/update triggers capture sanitized complete rows in changes, inside the same transaction as audits. Immutable triggers reject updates/deletes to original audit, corrections and feed rows. The collector can store these row objects then build analytical JSON-extraction views; for example `SELECT json_extract(data,'$.participant_id') participant_id,json_extract(data,'$.record_date') record_date,json_extract(data,'$.version_id') version_id FROM responses WHERE json_extract(data,'$.deleted_at') IS NULL`.

Task 3 must use `store.mutate(env,{id:'research',type:'system'},scope,{operation_id},async()=>Plan)` for durable job/usage/metadata/source/results updates. `Plan.changes` lists `{table,before,after}`; `newRow`, `updated`, `getRow`, `referenceGuards`, `check`, `activeReference` helpers preserve revision checks and audit/feed atomicity. Add canonical `catalogUrl` to recording matching; never infer canonical identity from the title. Candidate publication updates the response lookup job, keeps its query, and sets needs_review. Unambiguous resolution includes response before/revision plus job and catalog changes in one batch; response SQL unique indexes reject conflicts without loss. A version job is shared by version_id; unresolved jobs are unique by response_id. Admin manual_lock values must be preserved by research. The integration calls `registerResearchRunner(runResearchQueue)` from index.ts after imports/initialization, with research module depending on store/catalog rather than importing index (avoid a module cycle). The scheduled handler runs only with actual runner and both keys configured. No job is marked complete without a real runner.


## Research execution (Task 3)

The installed runner executes one durable stage per five-minute cron invocation: basic search, basic extraction, strict Groq inference, one catalog recording, one metadata claim, or response resolution. Jobs retain bounded source snapshots, validated analysis, stage and cursors; legacy jobs without a stage begin at search. A 90-second global lease prevents simultaneous provider calls. Expired leases and retryable HTTP failures have at most four attempts with bounded exponential backoff. 429 persists its cooldown and retains evidence, so retry resumes inference without spending search credits again. Admin retry restarts completed jobs and resumes unfinished stages. Keys missing means no calls and queued records remain intact.

Tavily `/usage` is checked before every paid-credit operation: Researcher free account, at most 1000 plan credits, no paygo consumption, and available account/key quota are required. A null per-key limit means the account allowance applies. D1 atomically reserves conservative credits before calls against the monthly cap (initial 800; administrator can lower or explicitly set up to 1000). Basic search costs one reserved credit; at most three basic-extract URLs reserve one additional credit. Failed or crashed reservations are retained conservatively. No automatic paid plan or advanced depth is used. A separate audited usage row counts attempted Groq requests and safe last-error codes.

Provider transport uses only the native Tavily/Groq REST endpoints with explicit application User-Agent, 20-second timeout, redirects rejected and a 48 KB streamed response ceiling. Search requests disable auto_parameters and answers; extraction uses two bounded chunks and the runner keeps at most 600 characters per source. Groq uses qwen/qwen3.8-27b, reasoning_effort none, strict json_schema and at most 1600 output tokens. The complete serialized schema, dictionary, query and output allowance are fitted to the conservative token budget by trimming source prefixes/titles (or reducing selected sources when necessary). Exact fitted source snapshots are persisted under the retained lease before inference; validation and publication use those same snapshots. The transport guard still blocks genuinely oversized caller requests; actual free quota and Workers CPU still need live acceptance measurement.

Inferred identities require recording URL evidence, title/artist agreement, an allowlisted source ID and a quote present in the retained text. Credits require the complete name in the same explicit matching role clause; crossing vocalist/composer clauses or clipping a name substring is rejected. English feat/featuring, Japanese role labels and combined Lyrics & Music attribution are supported; aliases require both names in a quote. Tags use the active 50-tag dictionary plus administrator additions (bounded dictionary read), a source quote and concrete AI rationale explaining the selected definition. Semantic inference is supported without literal tag-label occurrence; the assignment preserves `AI判定` rationale and quoted evidence. Title-only or unrelated performer-attribution quotations cannot establish genre/mood tags. AI judgement still requires administrator review when evidence is insufficient.

New recordings obtain independent shared version jobs initialized with the validated source/analysis cache. Response jobs await those metadata jobs, so changing/deleting an unresolved answer cannot strand shared catalog research. Canonical recording URL cache reuse requires retained title/artist evidence; title alone never merges versions. Ambiguous candidates remain owner-confirmable. Explicit original title/URL/relationship evidence links a cover/remix to an original work; absent links remain needs_review. Admin manual_lock fields are preserved, and all references/provenance are checked inside audited D1 transactions. Refreshed sources create immutable snapshots instead of silently replacing the evidence supporting older claims.

Cancelling an invitation and revoking devices retain historical grant rows. Participant deletion blocks active responses, active devices and unclaimed unexpired invitations, while permitting historical revoked/claimed/expired/cancelled grants. Response changes refresh lookup evidence/candidates; resolved/deleted responses tombstone their lookup jobs and expose only current version candidates.
